## 1. Бизнес-логика (единый словарь — не отступай)

**Owner-квартира** — квартира, купленная собственником и сдаваемая в аренду. Помечается флагом `is_owner`.

**Чьё имущество.** Только предметы категорий с `categories.kind = 'asset'` (мебель, техника, быт) могут принадлежать собственнику. Расходники (`kind = 'consumable'`) ВСЕГДА принадлежат компании, даже в owner-квартире (уборка списывает их со склада компании, как раньше).

**Где физически лежит имущество собственника:**
- в самой owner-квартире (все активы в owner-квартире считаются собственника этой квартиры);
- на складе компании, но на отдельной «полке собственника» — новая локация типа `owner_stock`, по одной на owner-квартиру. Это не общий склад компании: остатки, мин. запас, заказы поставщикам и средняя цена компании её НЕ учитывают.

**Правила перемещений (проверяются в одном месте — `_insert_move`):**
- актив собственника квартиры X можно двигать только между: внешним приходом (`source`), `owner_stock(X)`, квартирой X, списанием (`sink`);
- нельзя: в другую квартиру, на общий склад компании, сотруднику «на руки», от одного собственника к другому, и актив компании — в owner-квартиру;
- в `owner_stock` нельзя класть расходники.
Сообщение об ошибке одно и понятное: «Имущество собственника нельзя перемещать между собственниками или в имущество компании».

**Смена флага `is_owner`** разрешена, только если в квартире и на её полке owner нет активов с ненулевым остатком (иначе имущество компании «превратится» в имущество собственника). Иначе ошибка: «Сначала верните или спишите предметы (мебель, техника) из квартиры».

**Нормы** owner-квартир работают как есть (шаблон по типу + индивидуальные правки). «Наличие» = остаток в локации квартиры. Нехватку активов в owner-квартире «докомплектовать со склада» можно только с полки owner этой квартиры.

**Деньги, цены:**
- закупочная цена за единицу = как сейчас у компании: `avg_cost(item)` (средняя по приходам на склад компании);
- для имущества собственника — отдельная `owner_avg_cost(item, apartment)`: средняя по приходам именно этого собственника (внешний приход в его полку или сразу в его квартиру);
- расходы компании (отчёты, списания) и имущество собственников в отчётах НЕ смешиваются.

**Начисление жильцу** (деньги получает компания) — при подтверждении заявки (`incidents`) админом:
`сумма = round(qty × закупочная цена × коэффициент, 2)`.
- Коэффициент (`tenant_coef`, > 0, до 3 знаков, 1 = по закупке) задаётся вручную: на предмете (`items`) и на группе (`categories`; группа = категория).
- Приоритет: коэффициент, введённый в заявке → коэффициент предмета → коэффициент категории. Если нигде нет — начислить нельзя, пока админ не введёт его (молча «1» не подставлять).
- Цена и коэффициент ФИКСИРУЮТСЯ в момент подтверждения (снимок). Последующая смена коэффициента старые начисления не меняет.
- Жилец указывается текстом в заявке (отдельной таблицы жильцов нет и не нужно).
- Для owner-квартиры база = закупка собственника (`owner_avg_cost`), деньги всё равно получает компания.
- Заявка без предмета (`free_text`): цену и коэффициент вводят вручную.
- Статусы начисления: «К оплате» (`pending`) → «Оплачено» (`paid`) или «Не взыскивается» (`waived`); админ может вернуть в «К оплате». Нет строки начисления = не начисляется.
- По умолчанию переключатель «Начислить жильцу» ВКЛ для видов `lost`, `broken`, новый `damaged` («Порча»), и ВЫКЛ для `breakdown`, `other`. Админ может переключить.

## 2. База данных (новые миграции)

**Миграция A (отдельным файлом — enum нельзя использовать в той же транзакции):**

**Миграция B:**
1. `apartments.is_owner boolean not null default false`.
2. `locations.owner_apartment_id int unique references apartments(id) on delete cascade` + `check ((type = 'owner_stock') = (owner_apartment_id is not null))`. Существующие check-и по `apartment_id`/`staff_id` не трогай (для owner_stock они остаются верными).
3. `items.tenant_coef numeric(8,3) check (tenant_coef is null or tenant_coef > 0)`, то же в `categories`.
4. `stock_moves.owner_apartment_id int references apartments(id)` (null = компания) + индекс. Используется для отчётов и меток; остатки по-прежнему считаются по локациям.
5. Таблица `incident_charges`: `incident_id uuid primary key references incidents(id) on delete cascade`, `tenant_note text`, `base_cost numeric(16,6) not null check (>=0)`, `base_source text not null check in ('company','owner','manual')`, `coef numeric(8,3) not null check (>0)`, `amount numeric(14,2) not null`, `status text not null default 'pending' check in ('pending','paid','waived')`, `created_at timestamptz default now()`, `created_by uuid default auth.uid()`, `status_changed_at timestamptz`. RLS: select только админам (`is_admin()`), прямых insert/update/delete политик нет (пишут только RPC). `revoke all from anon`. Причина отдельной таблицы: супервайзеры читают `incidents` напрямую — цены и суммы им видеть нельзя. Проверь, что `delete_incident` и история работают с FK (cascade).
6. Функции:
   - `_loc_owner_stock(p_apartment int) returns int`;
   - `_loc_owner(p_loc int, p_item int) returns int`: вернуть `owner_apartment_id`, если локация `owner_stock`; вернуть `apartment_id`, если локация `apartment`, квартира `is_owner` и категория предмета `kind='asset'`; иначе `null`;
   - `owner_avg_cost(p_item int, p_apartment int) returns numeric` — по образцу `avg_cost`, но по движениям из `source` в `owner_stock(p_apartment)` или в локацию этой квартиры, с `unit_cost is not null`, без реверсов и без отменённых.

8. `_insert_move` — пересоздай с той же сигнатурой и прежним поведением, добавив: проверки правил перемещений из раздела 1 (нейтральны локации типов `source` и `sink`); запись `owner_apartment_id = coalesce(_loc_owner(from), _loc_owner(to))`; для движений в `sink` без явной цены: если есть owner — `owner_avg_cost(item, owner)`, иначе `avg_cost(item)` как сейчас.
9. `post_move` и `post_document`: добавь необязательный параметр `p_owner_apartment int default null` (старые вызовы продолжают работать):
   - `receipt` с `p_owner_apartment`: `source → owner_stock(X)` (только актив, X должна быть owner);

## 4. Критерии приёмки (проверь и отрази в отчёте)

1. Включение owner на пустой квартире — ок, создаётся полка owner. На квартире с активами — понятная ошибка. Снятие флага — по тем же правилам.
2. Приход на полку owner: `warehouse_stock`, `to_order`, `po_generate` и `avg_cost` компании НЕ изменились.
3. Выдача актива в owner-квартиру берёт со склада owner; расходник — со склада компании; «докомплектовать» работает так же.
4. Перемещение актива owner-квартиры в другую квартиру / на склад компании / сотруднику — отказ с единым сообщением, документ не создаётся.
5. Заявка `lost` на актив owner-квартиры: списание помечено owner, база начисления — закупка собственника, расходы компании в отчётах не выросли.
6. Приоритет коэффициента (заявка → предмет → группа); без коэффициента начислить нельзя; смена коэффициента в каталоге не меняет старые начисления.
7. Супервайзер и QR: видят бейдж OWNER и вид «Порча», но не видят цен, коэффициентов, сумм (проверь прямые `select` по `items`, `categories`, `incidents`, `incident_charges` под ролью супервайзера).
8. Все три языка, RTL, светлая/тёмная тема, 360px ширина.
9. Выполни и приведи результат: `npm run typecheck`, `npm run lint`, `npm run test`, `npm run check:i18n`, `npm run build`. Если что-то не удалось запустить (например, нет доступа к БД) — напиши прямо, что не проверено.

## 5. Не делать

Не добавлять таблицу жильцов/договоров, роли, уведомления, оплату онлайн, массовую установку коэффициентов, инвентаризацию полки owner, импорт/экспорт, новые зависимости. Не переписывать существующие миграции и не удалять дубли миграций (в репозитории есть парные файлы, например `approve_incident_in_progress`, `qr_shared_incidents_and_media` — только отметь в отчёте).

## 6. Формат отчёта

Список новых миграций (порядок применения), список изменённых файлов, что исправлено попутно, что НЕ проверено и почему.
